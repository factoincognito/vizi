L § 4 The CI reviewer (PO-68 pilot)
(1) While the pilot lasts, the workflow `.github/workflows/crog-review.yml`, a script on the Claude Agent SDK in `.github/reviewer/` (on Opus, paid by the organization's API credits), is Crog for this repository's PRs, except as this paragraph says. What it does is described in `docs/ROUTINES.md`, "CI review". Overrides § 34 (2) as to Crog running as an agent of Clead's session: while the pilot lasts, Crog also runs, for this repository's PRs, as this workflow, which this rule reads as a Claude Code agent under § 4 (3), since it runs on the Claude Agent SDK.
(2) What counts. Wherever the Rules require Crog's review, the review is the comment `Crog review: APPROVE` or `Crog review: CHANGES NEEDED`, ending `Head reviewed: <SHA>`, that `github-actions[bot]` posted. The merger accepts it only if its SHA is the PR's current head, the comment was never edited (`updated_at` equals `created_at`), and the `review` job of a `Crog review` run on that SHA succeeded. The same text typed by a session does not count. This guards against honest mistakes, not against someone with write access. A `Crog review: CHANGES NEEDED` that counts is a fix request: Crog may take its fixes from that comment (P-3 § 5 (2)).
(3) Merge gate. The CI check that gates a merge is `build`. A failed `Crog review` job (a key or credits that ran out, an outage) is not a CI failure; it is a head the workflow did not review. Overrides P-4 § 1 (3) as to the `Crog review` job.
(4) Not reviewed. For a head the workflow did not review (a fork, a failed run), a comment saying "Not reviewed" (a diff over its cap; that comment is not a verdict), and a PR whose base branch was changed after its review (the issue timeline has a `base_ref_changed` event dated after the verdict comment), Clead starts Crog as a separate agent on Opus. A manual Crog verdict on a head prevails over any CI verdict on it. A verdict is not redone when the base branch only moves on.
(5) Skipped. The workflow posts no review on a head whose changed files, compared with the PR's base branch, are only `docs/BACKLOG.md`, `CHANGELOG.md`, `STATUS.md` and `docs/NEXT_SESSION.md`. No manual Crog agent is started for such a head, unless the change is of a kind § 28 sends to review; then it is reviewed as under (4).
(6) Disagreement. An author who thinks a CI `CHANGES NEEDED` is wrong does not re-run the job or push an empty commit, and Clead does not start a manual Crog agent to get another answer; the question goes to Adam in accordance with Process P-3 § 6 (2), with both sides stated. The three-round limit counts the verdicts that can satisfy the gate. Overrides P-3 § 6 (1) for a disagreement with a CI verdict.
(7) Whose code. Code and config written by Crog are reviewed by Clead; on such a PR the CI verdict is extra. The PR description names who wrote the change; if it does not, both reviews are required: Clead's, and the CI verdict or a manual Crog verdict. A process change written by Crog is reviewed by Crog, as (11) says.
(8) Self-review. A PR that changes `.github/workflows/**`, `.github/reviewer/**`, L § 3, this paragraph or `memory/standards.md` is not reviewed by the workflow it may change: a separate Crog agent on Opus gives the required review, and a CI verdict on it is extra.
(9) Limits. The workflow only reads code and writes one PR comment. It never merges, approves through GitHub's review API or pushes; merging stays with the sessions.
(10) Model. The CI reviewer runs on Opus 5.5, set in `.github/reviewer/review.mjs`; moving it to another model is Adam's decision.
(11) Rules and process changes. Until the template ships its public copy of the product office's `RULES.md`, a CI verdict counts as Crog's review only for vizi code and config (§ 28 (1)(a)). A PR with a rules or process change (§ 28 (1)(b)) gets the review of a separate Crog agent on Opus, as under (4); a CI verdict on it is extra.
(12) End. The pilot ends when Adam ends it. This paragraph is then removed in a PR of its own.
