### 3.17 Version history (PBI-1.40)

The product owner's decisions: 2026-11-16, by voice, "the version history
feature should be used in our other apps also, such as vizi, wushroom,
acuteping" (PBI-1.40); and 2026-11-28 10:55, in chat, "Apyr" to Clead's
proposal of 10:53, on what a version of vizi is (item 2; "What is
decided", item 21). The feature is the Snake demo's (`sugose/snake-demo`,
`docs/spec/2.19-version-history.md`), which item 1 carries over. This
item is written for a web page that keeps its state in the browser's
local storage, as 3.14 does.

**Status:** intent approved by the product owner, 2026-11-28 12:49, in
chat, "Apyr", to Clead's recommendations of 11:44 on the three open
points below; recorded in `docs/spec/decided.md` item 22 and on the PR
that adds this section (#145).

In this section **[Clead]** marks Clead's proposals of 2026-11-28, which
are Clead's design within the approved intent, except what item 22
makes the product owner's: the copy of the code, the footer as the place
of the link and the version line (item 5), and that browsers that used
0.1.0 get no view for 0.2.0 (item 4). A mark at the head of an item
covers the item, but not what the item gives as his.

1. **Version history** (the product owner, as decided for the model).
   The page has a history of its versions. A "Version history" link
   opens it. The history opens by itself the first time the page is
   loaded after a version upgrade, and shows what is new. Its text is a
   list written for the page's users, one entry for each version, in
   plain words, built into the page; it is not `CHANGELOG.md`. After an
   upgrade only the versions newer than the last one this browser saw are
   shown, with a button to the full history. On a first visit, with no
   stored version, nothing opens; the link is always there.
2. **A version of vizi** (the product owner, 2026-11-28 10:55). A version
   is the `version` in `package.json`. A PR changes it on purpose, and
   the PR that does so adds that version's history entry (item 3). A
   merge that leaves the number alone is not an upgrade, whatever else
   it changes, although the page is published on every merge to `main`
   (2.2). The page shows the number (item 5). This settles what PBI-1.37
   left open about what a version is and how it is set; where it shows is
   item 5.
   - **[Clead]** The form: three whole numbers joined by dots, each
     written without a leading zero (`0.2.0`, `1.10.0`), and nothing
     else: no `v`, no space, no prerelease or build part. Two versions
     are compared number by number, as numbers of any length, and the
     first difference decides (`0.9.0` is lower than `0.10.0`), by a
     function of its own in `src/history.ts`; no third-party code. A
     `version` in `package.json` in another form fails the test of item
     3.
   - **[Clead]** The build gives the number to the page: `vite.config.mts`
     reads `version` from `package.json` and passes it to the code as a
     build-time constant (Vite's `define`). The page reads no file and
     makes no request for it, and the page's requests and its
     Content-Security-Policy stay as 2.3 sets them; only the hashes of
     the inline script change with the build, as with any change to it.
     The functions of `src/history.ts` take the version as an argument,
     so Jest tests them without a build. V is the one input of item 4 that
     the page does not read from the browser, and the page still checks
     it: a V that is not of the form means nothing opens, nothing is
     written and the footer line reads "Version history" without a
     number; the Jest test of item 3 makes sure the shipped one is of
     the form, so this is a guard against a bad build.
3. **The list** (**[Clead]**). The list is data in `src/history.ts`,
   newest first, in English like the rest of the page. An entry has a
   version (item 2's form), a date written `YYYY-MM-DD` that is a real
   calendar date (`2026-02-30` is not), and one or more lines, each a
   text that is not empty and not only spaces. A line is shown as text,
   never as HTML. No two entries have the same version, and the list is
   in descending order of version. The `version` of `package.json` has
   an entry and it is the first, so a version cannot be set without
   writing what it brings; a Jest test checks it. Nothing of the list is
   read from the network, a file or the store when the page runs. The
   list starts with two entries: 0.1.0 for the page as it was before the
   history, and 0.2.0 for the history itself. The product owner
   accepted that the history starts at 0.2.0 with those two entries
   (`docs/spec/decided.md` item 21); the date of each entry and the
   texts are Clead's to write in the code PR, which sets `version` to
   `0.2.0`, and the product owner approves the texts there (product-office
   `RULES.md` § 7 (2)). The date of an entry is the day its version is
   set; the test does not compare it with the clock.
4. **What opens by itself** (**[Clead]**). The version last seen is
   kept in the browser's local storage (item 7). When the page loads,
   with S the stored text and V the build's version:
   - S is missing, or is not of the form of item 2, or reading it
     throws, or the storage cannot be got hold of: nothing opens. In
     each of these cases V is written; the write is tried inside the
     error handling, and a failure of it is ignored.
   - S equals V or is higher (a build older than the one this browser
     saw last): nothing opens, and V is written.
   - S is lower than V: the view of item 6 opens by itself with the
     entries of versions higher than S and not higher than V, newest
     first, and V is written. If there is no such entry, nothing opens.
   The write is made at load, not when the view closes. So while the
   storage works a version opens by itself once in a browser, whatever
   the user does with the view; a second tab loaded before the first has
   written would open it too. A write that fails is ignored, and the
   view may open again at the next load. The case "no such entry"
   cannot happen with the list as built (item 3 puts V in it) and is a
   case of the function only. A browser that loaded the page as 0.1.0
   stored nothing, so its upgrade to 0.2.0 opens nothing, and the 0.2.0
   entry is shown by itself to nobody; the first upgrade to open the
   view is the one after 0.2.0 (open point 4). A load that the page starts at startup
   from `?repo=` (3.16) goes on as 3.10 says for a load under way: it
   fills the start page unseen behind the view, which is there when the
   view closes.
5. **The link and the version line** (**[Clead]**). The page's footer
   (3.12) gets a line above the font notice: "Version 0.2.0" (the build's
   version), a space, the middle dot U+00B7, a space, and a
   `<button type="button">` "Version history", styled as a link as the
   help control is (3.10): it acts inside the page and goes nowhere. The
   footer is where the font notice and the notices link already are, and
   the page's header holds only the help control. The line wraps on a
   phone; the page does not scroll sideways (3.12).
6. **The view** (**[Clead]**). The view is built as the help view is
   (3.10): a `<section>` in `<main>`, sibling of the start wrapper, with
   `hidden` set while it is closed. Opening it sets `hidden` on the
   wrapper, on the help control and on the footer, as 3.10 says for the
   help view, so neither view can be opened while the other is. Nothing
   is removed or cleared, and a load under way carries on unseen; the
   view starts no load and cancels none.
   - Opened from the link, its title (an `h2`) is "Version history" and
     it shows every entry, newest first. The link is in the footer,
     which opening hides, so the focus goes to the top "Back to vizi"
     button as the view opens.
   - Opened by itself (item 4), its title is "What's new" (with the
     apostrophe U+0027), it shows the entries item 4 names, newest first,
     and below them a button "Show full history". Pressing it shows
     every entry under the title "Version history", removes the button
     and puts the focus on the top "Back to vizi" button.
   - An entry is a heading (`h3`) "Version 0.2.0 · 2026-11-28" (the
     version, a space, U+00B7, a space and the date) with its lines as a
     list under it, in the order of the data.
   - It closes with a "Back to vizi" button at its top and again at its
     end, or with the Escape key; Escape with the view closed does
     nothing. Closing removes `hidden` from the wrapper, the help control
     and the footer, which show the current state, as 3.10 says. The
     focus then goes to the "Version history" link. When the view opened
     by itself, the focus goes to the top "Back to vizi" button as it
     opens; that is an exception to 3.16's "The focus is not moved", for
     this one case (item 10).
   - It has the look of the help view: the same width, headings and
     spacing, in the light, dark and phone forms of 3.12. It scrolls with
     the page and never sideways.
7. **What is stored** (**[Clead]**). The version last seen is kept in
   `localStorage` under the key `vizi.seenVersion`, as the version's
   text, not as JSON. It is the one write at a load that is made when
   nothing of vizi's is in storage (3.8 and 3.14 write a cleaned value
   back at startup, only when a stored value of theirs was bad; 2.2 and
   3.9 say what is stored, and item 10 lists what changes there).
   It is read once at load and written once (item 4);
   closing the view writes nothing. It is not a secret and holds no
   token. It is on the shared origin (2.2, "One origin for every
   factoincognito Pages site"), so any page on `https://factoincognito.github.io`
   can read and write it. The most a script there can do is make the
   view open, or stay shut, in this browser; a stored text that is not of
   the form of item 2 counts as missing, and the page trusts nothing in
   it beyond item 4's rule. Every access to the storage, getting hold of
   it included, happens inside error handling, as in 3.8 and 3.14, and
   the page goes on when it fails.
8. **No address** (**[Clead]**). As 3.10 says of the help view: the view
   has no hash and no history entry, and a reload shows the start page
   (or what `?repo=` opens, 3.16), never the view. It cannot be linked
   to.
9. **Tests** (**[Clead]**), test first. The Jest environment is `node`
   (`package.json`), so Jest tests functions, not the page; the page is
   tested in Playwright against the built page.
   - Jest, `src/history.test.ts`. The list is checked by a function,
     `checkHistory(list)`, that returns what is wrong with a list, and
     the tests give it lists that are wrong as well as the shipped one:
     an empty list; an entry with a version of the wrong form, a
     repeated version, an ascending order, a date such as `2026-02-30`,
     `2026-2-3` or empty, no lines, an empty line, a line of spaces
     only. The shipped list has no problem, and its first entry is the
     `version` of `package.json` (a test reads the file).
   - The rendering path, as `src/help.test.ts` does for 3.10: `src/history.ts`,
     the file that builds the view if it is not `src/main.ts`, and
     `src/main.ts` hold no `innerHTML`, `outerHTML` or
     `insertAdjacentHTML`, and `src/history.ts` holds no import, no
     `fetch` and no `XMLHttpRequest`. The existing check there names
     `help.ts` and `main.ts` only, so this one is its own.
   - The form: accepts `0.2.0`, `1.10.0`, `0.0.0`; refuses the empty
     string, `v0.2.0`, ` 0.2.0`, `0.2.0 `, `0.2.0\n`, `0.2`, `0.2.0.1`,
     `00.2.0`, `0.02.0`, `0.2.0-rc.1`, `0.2.0+a`, `-1.0.0`, and a version
     written in non-ASCII digits (`０.２.０`, Arabic-Indic digits).
   - The comparison: `0.9.0` < `0.10.0` < `0.11.0`, `0.99.99` < `1.0.0`,
     equal versions equal, and numbers longer than a machine integer
     (`0.18446744073709551615.0` < `0.18446744073709551616.0`).
   - Item 4's decision, with the store given as an argument that is a
     store, a store that throws on reading, a store that throws on
     writing, or nothing (the case of a storage that cannot be got hold
     of): S missing; S not of the form; S equal to V; S higher than V;
     S lower than V with one, several and no entry in between, the
     entries given newest first; V itself not of the form (nothing
     opens, nothing is written); in each case what was written. The
     getter that throws is `browserStorage()` in `src/main.ts`, which
     Jest does not reach; Playwright covers it (below).
   - Playwright, `e2e/history.e2e.ts`, with GitHub's answers stubbed and
     no request beyond 2.3's. The list under test is the shipped one,
     read by the test from `src/history.ts`.
     - The footer line shows the version of `package.json` and the link.
       The link opens the view with the title "Version history", every
       entry newest first, each heading of item 6's form, and each
       line's text equal to the data, and only the elements item 6 names.
       This does not prove that a line is shown as text, since the
       shipped lines hold no markup; no hook in the page lets a test
       give it a line with `<` in it, and none is added, since any
       script on the shared origin could use it. The proof is the
       source check of Jest (above).
     - "Back to vizi" at the top and at the end, and Escape, close the
       view, put the focus on the link, and show the wrapper, the help
       control and the footer again; opened from the link, the focus is
       on the top "Back to vizi" button; Escape with the view closed
       does nothing (the help view stays closed, the focus stays);
       closing writes nothing (the key holds the same text before and
       after).
     - With `vizi.seenVersion` set to `0.1.0` before the page loads
       (`addInitScript`), the view opens by itself with the title
       "What's new", the entry of 0.2.0 only and the button, the focus
       is on the top "Back to vizi" button, the key holds the build's
       version after the load, and the button shows every entry under
       "Version history", is gone afterwards and the focus is on the
       top "Back to vizi" button. With the key missing, equal to the
       build's version, higher, or not of the form, nothing opens and
       the key holds the build's version.
     - With `?repo=` and an older stored version, the view opens and
       the load's result is on the start page when it closes (3.16).
     - The help control is hidden while the view is open and the view
       cannot be opened while the help view is.
     - The address: `location.href`, `location.hash` and
       `history.length` are the same before opening, with the view open
       and after closing, and a reload shows the start page (item 8).
     - A storage whose getter throws (`Object.defineProperty` on
       `window.localStorage` in `addInitScript`), a `getItem` that
       throws and a `setItem` that throws each leave the page working
       with nothing opened, and no console error that is not the
       page's own handled one.
     - The contrast of every visible text element of the view, in the
       light and dark forms, is as 3.12 requires of the start page; the
       Content-Security-Policy of 2.3 and its test hold with the view
       open (no violation, no request); no sideways scrolling at 375 px.
   - The subpath check of 3.6 and the browser tests' stray-request guard
     stay as they are.
10. **What changes elsewhere** (**[Clead]**). The page's first write at
    a load is new, and the footer is no longer only the font notice. The
    code PR changes these together with the code, and they are listed
    here so that none is found by a red test:
    - Sentences that say nothing is stored or written: 2.2 ("Before
      PBI-1.8 it held nothing secret and stored nothing…", and the
      list of keys that follows it, which gains `vizi.seenVersion`),
      3.9 ("nothing is written to the browser's storage": about the
      umbrella view's tree, so it gets "except the key of 3.17"),
      and 3.8's "The shared origin" list, where a script on the origin
      can write values of its own: it gains the effect of item 7.
    - Tests that assert an empty storage or the exact keys:
      `e2e/token.e2e.ts` (`localStorage.length` is 0 at lines 325, 906,
      1206, 1392, 1467 and 1537; `Object.keys(localStorage)` equals
      `[KEY]` at line 341) and `e2e/umbrella.e2e.ts` (lines 272 and
      451). They count the keys other than `vizi.seenVersion` (a helper
      in `e2e/`), so they still assert what they were written for,
      that no token or repo name is stored.
    - The footer: 3.12-a (the page's third part) and 3.12-b (the
      accessibility list: the tab order, which gains the button, "Escape
      stays the help view's" gains the version view, and step 2 of the
      "What opening hides" list) say what the footer holds; `e2e/start.e2e.ts`
      lines 548-553 assert its exact text and lines 419-455 the list of tab
      stops, which gains the "Version history" button before
      `notices-link`, the footer's last control.
    - 3.16's "The focus is not moved" and its test "the focus is on
      `document.body` after the startup open": they hold unless the view
      opens by itself, which moves the focus to its top "Back to vizi"
      button (item 6). The 3.16 test sets `vizi.seenVersion` to the
      build's version, so it keeps asserting what it asserts.
    - `package-lock.json` holds the version twice (as `"version"` of the
      package at the top and under `packages[""]`); the code PR changes
      both, and `npm ci` is run on the result.

**Not in this item.**

  written from the rules above and not shared with the Snake demo or

- `CHANGELOG.md` stays the record of merged PRs and is not the history.
- Release tags and a version in the page's title: none.

**Decided by the product owner, 2026-11-28 12:49** ("Apyr" to Clead's
recommendations): (1) the code is copied, not shared; (2) the link and
the version line are in the footer; (3) the upgrade to 0.2.0 opens
nothing for browsers that used 0.1.0, because the only way to show it
to them, treating a missing stored version as 0.1.0, would show the
"What's new" view to every first-time visitor too.
